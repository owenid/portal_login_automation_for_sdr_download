AWS architecture reference

Gradwell CDR Pipeline

A scheduled Lambda that logs into the Gradwell SSO/Admin portal, downloads the latest SDR call-detail-record file, and stores it in S3 — running unattended on the 1st of every month.

System diagram

What each component does

AWS EventBridge Scheduler
Trigger
MonthlyCdrDownloadSchedule fires the Lambda on cron(0 9 1 * ? *), evaluated in the Europe/London timezone — a fixed 09:00 UK local time every 1st of the month, year-round. Scheduler applies the GMT/BST transition automatically (unlike a classic EventBridge Rule, which is UTC-only), and invokes the function directly via SchedulerInvokeRole, an IAM role scoped to lambda:InvokeFunction on just this function. Nothing else in the system runs unless this schedule fires, or someone invokes the function manually for testing.
AWS Lambda
Compute
CdrDownloaderFunction — the entire mechanism runs inside one invocation. Node.js 22.x on x86_64, 2048 MB memory, a 180-second timeout, and 1024 MB of /tmp. Drives a real headless Chromium session via playwright-core and @sparticuz/chromium to perform the login, navigation, and file download exactly as a person would in a browser. Measures its own wall-clock duration and returns it as durationMs in the response (and logs it on failure too), so a run creeping toward the timeout is easy to spot.
IAM execution role
Access control
Scoped narrowly on purpose: secretsmanager:GetSecretValue only on the named secret's ARN pattern, and s3:PutObject limited to the cdr/* and debug/* prefixes of the CDR bucket — not the bucket as a whole. The function holds no broader AWS permissions — it can't read other secrets, write outside those two prefixes, or touch other buckets.
AWS Secrets Manager
Secret
prod/AdminPortal/Gradwell holds the portal username and password as a JSON key pair. Pre-existing — this stack reads it but never creates, owns, or writes its value. Fetched fresh on every invocation; never cached, logged, or written to disk.
Gradwell SSO / Admin Portal
External system
Not part of this AWS account — a third-party customer/reseller portal reached over the public internet. The Lambda logs in at sso.prod.gradwell.com, lands on admin.prod.gradwell.com/home, then /cdrs, where a table sorted newest-first lists each billing period. On the 1st of the month it first confirms the newest row's End Date is the last day of the previous month — the period that should have just completed — and throws an error instead of downloading if Gradwell hasn't published it yet; otherwise it clicks the first row's download control to fetch the latest CDR file.
Amazon S3
Storage
CdrBucket — private, SSE-AES256 encrypted, all public access blocked. Downloaded files land under cdr/<year>/<month>/; optional per-step debug screenshots land under debug/ and auto-expire after 30 days via a lifecycle rule.
Amazon CloudWatch Logs
Observability
Every invocation's console output — including full Playwright error traces and the 1st-of-month freshness check's error message — lands automatically in the function's log group, /aws/lambda/gradwell-cdr-downloader, kept for 400 days (the LogRetentionInDays parameter). The source of truth for why a run succeeded or failed.
CdrDownloaderErrorsAlarm
Alerting
CloudWatch alarm on the function's Errors metric (namespace AWS/Lambda). Uses a 1-day evaluation period with TreatMissingData: notBreaching, since the function only runs once a month — an idle day reads as "no data," not a failure. If DatadogForwarderTopicArn is set, it publishes ALARM/OK transitions to that SNS topic for the Datadog Forwarder to consume; left unset (the default), the alarm still exists and is visible via CloudWatch, just without an external notification target.

What happens on any failure

  1. The failing step throws an error with a code (CDR-E01–CDR-E11), the step name, the reason, and — when a browser page is open — the page URL, title and any on-page error message.
  2. The catch block saves a full-page screenshot and the page HTML to S3 at debug/<run-id>/99-failure.png and 99-failure.html. This always happens; DebugScreenshots only adds the per-step screenshots.
  3. It writes a JPEG screenshot to CloudWatch Logs on a line starting FAILURE_SCREENSHOT_BASE64.
  4. It writes a CDR_DOWNLOAD_FAILED JSON line to CloudWatch Logs with code, step, reason, runId, durationMs and the two S3 paths.
  5. It rethrows. The invocation's errorMessage (what aws lambda invoke writes to out.json) reads [CDR-Exx] <step> failed: <reason> Failure screenshot: s3://….
  6. It publishes CdrDownloader / Failures with the error code as a dimension, shown on the monitoring dashboard.
  7. AWS adds 1 to the Errors metric, which trips CdrDownloaderErrorsAlarm and, if configured, Datadog.
  8. Lambda retries a failed scheduled run twice, a few minutes apart, so one failed month can log up to three CDR_DOWNLOAD_FAILED lines.

Exception — timeout: a run that reaches the 180-second Lambda timeout is stopped before steps 2–5 can run. It logs only Task timed out after 180 seconds, with no code and no screenshot, but still counts as an error, so the alarm and retries still happen.

How to investigate a failure

  1. Read the code and message in out.json, or search CloudWatch Logs for CDR_DOWNLOAD_FAILED.
  2. Look up the code below for what it means and what to do.
  3. Open the screenshot: download the S3 path from the message, or decode the latest CloudWatch copy with aws logs filter-log-events --log-group-name /aws/lambda/gradwell-cdr-downloader --filter-pattern '"FAILURE_SCREENSHOT_BASE64"' --query 'events[-1].message' --output text | sed 's/.*FAILURE_SCREENSHOT_BASE64 //' | base64 -d > failure.jpg
  4. If a selector needs changing, use 99-failure.html to find the right element.
  5. Fix, redeploy if needed, then re-invoke (see Recovery below).

Error codes

CDR-E01 · Credentials fetch failed
Secrets Manager
The secret prod/AdminPortal/Gradwell couldn't be read, isn't valid JSON, or is missing username/password. Happens before the browser starts, so there is no screenshot. [CDR-E01] Fetching portal credentials from Secrets Manager failed: <AWS error>. No browser page was open.
What to do: Check the secret exists in eu-west-2 with both keys, and that the function role can read it.
CDR-E02 · Browser failed to start
Lambda runtime
Headless Chromium couldn't launch — usually a dependency or memory problem after a @sparticuz/chromium upgrade. No screenshot is possible. [CDR-E02] Launching the headless browser failed: <error>. No browser page was open.
What to do: Re-check the @sparticuz/chromium / playwright-core versions and the 2048 MB memory setting.
CDR-E03 · SSO login failed
Gradwell SSO
The login form fields or button weren't found, or the login didn't complete — wrong credentials, a changed login page, or an extra step such as MFA. [CDR-E03] Logging in to Gradwell SSO failed: timed out (locator.fill: Timeout 30000ms exceeded, waiting for locator('…')). Page URL: …; page message: "…".
What to do: Open the failure screenshot. If the password changed, update the secret; if the page changed, update SELECTOR_USERNAME_INPUT, SELECTOR_PASSWORD_INPUT or SELECTOR_LOGIN_BUTTON.
CDR-E04 · Admin home page didn't open
Gradwell Admin
Neither clicking Admin nor going straight to /home worked — often means the login didn't actually succeed. [CDR-E04] Opening the Admin home page failed: <reason>. Page URL: …
What to do: Check the screenshot for a login error or expired session, then the ADMIN_HOME_URL setting.
CDR-E05 · CDR page didn't open
Gradwell Admin
Navigating to /cdrs itself failed (timeout or network error) before any table check. [CDR-E05] Opening the CDR page failed: <reason>. Page URL: …
What to do: Re-run; if it repeats, check the portal is up and the CDR_URL setting.
CDR-E06 · CDR table missing
Gradwell CDR page
The CDR page opened but no table rows appeared within 30 s. The page's own message is quoted — on 1 Oct 2026 this was "customer is required", meaning no customer was selected. [CDR-E06] Opening the CDR page failed: the CDR table did not appear within 30s (no element matched "table tbody tr"). Page URL: https://admin.prod.gradwell.com/cdrs; title: "…"; page message: "customer is required".
What to do: Act on the quoted page message. For "customer is required", the automation must select the customer (or open the customer-specific CDR URL) before the table can load.
CDR-E07 · End Date cell not found
1st of month only
The table loaded but the newest row's End Date cell (SELECTOR_LATEST_END_DATE_CELL) isn't there — the table's columns differ from what's expected. [CDR-E07] Checking the newest CDR period is published failed: could not find the "End Date" cell of the newest CDR row (no element matched "…" within 30s) …
What to do: Use 99-failure.html to find the right column and update SELECTOR_LATEST_END_DATE_CELL.
CDR-E08 · End Date unreadable
1st of month only
The End Date cell was found but its text isn't a date — the column order or date format has changed. [CDR-E08] Checking the newest CDR period is published failed: could not parse the newest CDR period's end date from "…" — the CDR table format may have changed.
What to do: Compare the quoted text with the table in the screenshot and fix the selector or the date parsing.
CDR-E09 · New period not published yet
1st of month only
The newest row ends before the last day of the previous month — Gradwell hasn't published the new CDR yet. Not a bug in the automation. [CDR-E09] Checking the newest CDR period is published failed: new CDR record not yet available: expected the newest CDR period to end 2026-09-30 …, but the newest row on the page ends 2026-08-31 …
What to do: Wait for Gradwell to publish, then re-invoke manually. The check only runs on the 1st, so a re-run on a later day downloads the newest row without it.
CDR-E10 · Download failed
Gradwell CDR page
No download started after clicking the newest row's download control, or the download broke partway through. [CDR-E10] Downloading the CDR file failed: timed out (page.waitForEvent: Timeout 60000ms exceeded while waiting for event "download") … — or — … failed: Download failed: <reason>.
What to do: Check the screenshot for a missing or moved download icon and update SELECTOR_DOWNLOAD_BUTTON; re-run if it was a network blip.
CDR-E11 · S3 upload failed
Amazon S3
The CDR file downloaded but PutObject to cdr/… failed — permissions or network. [CDR-E11] Uploading the CDR file to S3 failed: <AWS error>.
What to do: Check the bucket exists and the role's prefix-scoped s3:PutObject permission.
CDR-E99 · Unexpected error
Anywhere
Something failed outside the named steps (should be rare). The message is the raw error. <raw error message> — logged with "code":"CDR-E99".
What to do: Read the stack field of the CDR_DOWNLOAD_FAILED log line.

AlarmsErrors · delivery missing · file too small
! Datadog alerting is optional and off by default. Three alarms exist regardless: CdrDownloaderErrorsAlarm on the Errors metric, delivery-missing (no file of at least 1 KB by the 10:30 delivery check on the 1st) and file-too-small (a saved file under 1 KB). The CdrDownloaderDashboard shows them with the five monitoring metrics. Their ALARM/OK state only reaches Datadog once DatadogForwarderTopicArn is set to a real Forwarder SNS topic ARN (sam deploy --parameter-overrides DatadogForwarderTopicArn=<arn>) — until then, check the alarm directly via CloudWatch or aws cloudwatch describe-alarms. Note that a legitimate ALARM on the 1st of the month can now also mean "Gradwell hasn't published this period yet" rather than a real bug — check the CloudWatch Logs message before treating it as an incident: that case is error code CDR-E09. The SNS topic must be in eu-west-2, the same region as the alarm.
